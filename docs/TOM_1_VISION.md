# Глава 1

# Цель проекта

## Что создается
Создается профессиональная настольная CRM-система управления сетью торговых точек.

Это не учебный проект.

Не демонстрационный проект.

Не MVP.

Не тестовое приложение.

Проект должен постепенно вырасти в полноценную коммерческую систему, которой ежедневно пользуется администратор сети торговых точек.

---

## Основная задача проекта
Полностью заменить ручное управление персоналом.

После завершения разработки администратор должен иметь возможность управлять всей сетью магазинов из одного приложения.

Без Excel.

Без блокнотов.

Без Telegram-чатов.

Без бумажных отчетов.

---

Программа должна стать единым центром управления.

---

# Основные функции системы
Система должна позволять:

• управлять торговыми точками

• управлять сотрудниками

• назначать сотрудников на несколько точек одновременно

• создавать задачи

• назначать задачи

• контролировать выполнение задач

• принимать отчеты

• контролировать смены

• просматривать статистику

• отслеживать нарушения

• хранить историю

• работать полностью офлайн

---

# Главная идея проекта
Программа должна помогать администратору.

Она не должна усложнять работу.

Каждое действие должно требовать минимального количества кликов.

Любая информация должна находиться максимум за несколько секунд.

---

# Основной принцип

оно должно быть упрощено.

Если можно убрать один клик —

его необходимо убрать.

Если можно автоматизировать действие —

его необходимо автоматизировать.

# Глава 6

# Что такое РоссТабак Manager
РоссТабак Manager — это единый центр управления всей сетью торговых точек.

Проект не должен восприниматься как набор отдельных экранов.

Он представляет собой единую систему, в которой все сущности взаимосвязаны.

Каждое действие пользователя влияет на другие модули системы.

Например:

- сотрудник назначается на одну или несколько торговых точек;
- задачи назначаются сотрудникам;
- задачи относятся к конкретной торговой точке;
- выполнение задач влияет на отчёт смены;
- отчёт смены влияет на статистику;
- статистика отображается на Dashboard;
- Dashboard отображает текущее состояние всей сети.
Никакой модуль не должен существовать изолированно.

---

# Глава 7

# Главная концепция
В основе проекта лежит три главные сущности.

## 1. Торговая точка
Это основная единица бизнеса.

Все остальные сущности так или иначе относятся к торговой точке.

Каждая точка имеет:

- название;
- адрес;
- станцию метро;
- цветовой маркер;
- сотрудников;
- задачи;
- отчёты;
- историю.
Точка не должна хранить лишнюю информацию.

Она хранит только собственные данные.

Все связи реализуются через отдельные сущности.

---

## 2. Сотрудник
Сотрудник никогда не принадлежит только одной точке.

Архитектура сразу должна поддерживать работу сотрудника на нескольких торговых точках.

Связь должна строиться через отдельную таблицу.

```
Employee

↓

EmployeeStores

↓

Store
```
Это обязательное требование.

Запрещается использовать поле

```
storeId
```
в таблице сотрудников.

Используется только связь многие-ко-многим.

---

## 3. Задача
Задача является самостоятельной сущностью.

Она не принадлежит сотруднику.

Она не принадлежит точке.

Она связывается через ссылки.

Это позволит в будущем:

назначать нескольким сотрудникам

назначать нескольким точкам

создавать повторяющиеся задачи

делать шаблоны задач

создавать категории задач

создавать архив задач

# Глава 14

# Главная цель интерфейса
Администратор должен открывать программу утром и видеть всё состояние бизнеса на одном экране.

Он не должен искать информацию.

Информация должна сама показывать, что требует внимания.

Например:

- сколько сотрудников сейчас работают;
- какие смены открыты;
- сколько просроченных задач;
- сколько отчётов не отправлено;
- какие торговые точки требуют внимания.
Dashboard должен стать центром принятия решений, а не просто стартовым экраном.

# Глава 15

# Принцип развития проекта
Каждая новая функция должна отвечать на три вопроса:

1. Решает ли она реальную задачу администратора?
2. Вписывается ли она в существующую архитектуру?
3. Не усложняет ли она интерфейс?
Если ответ на любой вопрос отрицательный, функцию необходимо переработать до начала реализации.

---

# Инструкция для ИИ (обязательна)
Перед созданием любого нового класса, файла или экрана необходимо выполнить следующие проверки:

1. Существует ли уже аналогичный компонент?
2. Можно ли переиспользовать существующую модель или виджет?
3. Соответствует ли новое решение общей архитектуре проекта?
4. Не создаёт ли изменение зависимость между независимыми модулями?
5. Будет ли это решение масштабироваться через год без переписывания?
Если хотя бы один ответ отрицательный, реализацию следует пересмотреть до написания кода.
